# KYN VPN: сайт и email-кабинет

Сайт находится в `bot/bot/portal/`, запускается вместе с существующим FastAPI.
Он не требует Telegram и не создаёт фиктивных Telegram ID. Email-аккаунты,
заказы и подписки хранятся в отдельных таблицах PostgreSQL. Клиенты XUI
называются `web.<subscription UUID>`; существующие ключи бота не меняются.

## Сценарии

- `/web/`: главная, действующие тарифы из `CONFIG.month_cost`, инструкция и FAQ.
- `/web/privacy` и `/web/terms`: публичные страницы обработки данных и условий покупки;
  доступны без авторизации, используют общий стиль сайта. По указанию владельца
  компания/бренд обозначены как KYNVPN, без вымышленных реквизитов.
- Вход по одноразовому шестизначному коду через SMTP с TLS. Код действует
  10 минут, допускает пять попыток; повторное использование запрещено.
- Ограничения через Redis: три письма на email за 15 минут, 20 на IP в час,
  ограничение попыток проверки, оформления заказов и запросов к панели.
- Сессия на семь дней: случайный токен в Secure/HttpOnly/SameSite=Lax cookie;
  в БД хранится SHA-256 токена. Logout удаляет серверную сессию.
- Все запросы изменения состояния проверяют Origin. Нет CORS для чужих сайтов.
- Кабинет: срок подписки, история заказов, продление, копирование основного
  профиля и XHTTP, скачивание профилей; закрытый доступ по владельцу аккаунта.
- Оплата разовая, через существующий кошелёк YooMoney. Цены берутся на сервере,
  сумма клиента игнорируется. Переход на successURL не подтверждает оплату.
- Нативные уведомления проверяются HMAC-SHA256 (`sign`), включая сумму до
  комиссии (`withdraw_amount`), валюту, статус и label. Дубликаты не продлевают
  срок повторно. Идентификатор операции уникален в БД. Подпись использует
  RFC 3986 (`%20` для пробелов). Подписанные `test_notification=true` подтверждают
  доставку без начисления доступа; уведомления бота `vb2_*` подтверждаются без
  начисления в web-кабинете — их проверяет существующий worker бота.
- После оплаты сначала фиксируется абсолютный срок и объём, затем создаётся
  или обновляется один клиент XUI на основном и резервном inbound. UUID
  сохраняется при повторах. Отказ панели оставляет оплату учтённой: повторное
  уведомление или кнопка в кабинете повторят настройку без новой оплаты.
- Доступ истекает на стороне XUI по `expiryTime`, даже если бот остановлен.

## Локальный просмотр

```bash
python3 scripts/preview_portal.py
# http://127.0.0.1:8099/web/
# Отдельный просмотр кабинета с примерными данными:
python3 scripts/preview_portal.py --port 8100 --account
# http://127.0.0.1:8100/web/#account
```

Это только просмотр дизайна с явно помеченными примерными ценами: письма,
аккаунты и оплаты не создаются. Основные сценарии API проверяются отдельными
тестами с локальной БД и подменами SMTP/XUI, без реальных платежей.

```bash
.venv/bin/python -m pytest tests/test_web_portal.py tests/test_xhttp_subscription.py tests/test_yoomoney_webhook.py -q
docker compose build vpn_hub_bot
```

Проверено при разработке: 18 основных проверок пройдены; отдельно пройдена
проверка миграции и четырёх одновременных одинаковых платежных уведомлений
на изолированной PostgreSQL 16.4 (срок и квота начисляются один раз).
Сборка Docker и компиляция ru/en локализаций успешны. Главная страница,
выбор тарифа и окно входа проверены в браузере на desktop и ширине 390 px.

Дополнительная PostgreSQL-проверка (только локальный тестовый контейнер):

```bash
docker run --rm --name vpnhub-portal-test-db -d \
  -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=portal_test \
  -p 127.0.0.1:15489:5432 postgres:16.4
# Дождаться готовности pg_isready внутри контейнера.
PORTAL_TEST_POSTGRES=1 .venv/bin/python -m pytest tests/test_web_portal.py -q
docker stop vpnhub-portal-test-db
```

## Перед публикацией

1. Утвердить HTTPS-адрес и размещение. На текущем VPN-сервере TCP 443 занят
   основным REALITY. Нельзя ставить на него обычный HTTPS Nginx, вытеснив Xray.
   Нужен отдельный web ingress/сервер либо отдельно согласованная схема
   совместного использования порта. `configs/portal/nginx.conf.example` —
   шаблон отдельного ingress, не готовая замена действующего VPN listener.
2. Настроить SMTP и домен отправителя у выбранного почтового провайдера.
   Проверить доставку на российские почтовые сервисы с тестовым адресом,
   предоставленным владельцем. Пароли хранить в окружении сервера.
3. Перенести переменные из `configs/portal/portal.env.example` в защищённое
   окружение приложения. Создать независимый `PORTAL_SECRET`.
   `PORTAL_ENABLED` по умолчанию выключен. API не открывается автоматически.
4. Указать адрес поддержки и утверждённые страницы условий/обработки данных.
   Тексты от имени владельца не выдуманы. Без этих URL checkout выключен;
   без privacy URL и SMTP нельзя запрашивать код.
5. Убедиться в актуальности `MONTH_COST` на production: локальный `.env` может
   содержать тестовые цены. Сайт использует именно текущие серверные значения,
   не примерные цены локального просмотра.
6. Настроить доставку `kw1_*` уведомлений на `/web/api/payments/yoomoney`.
   YooMoney имеет один URL уведомлений на кошелёк: **не заменять действующую
   схему бота вслепую**. Существующий `/payments/yoomoney/webhook` уже умеет
   направлять form-urlencoded `kw1_*` в обработчик сайта, сохраняя прежнюю
   проверку токена для остальных платежей. Если используется промежуточный
   шлюз, он должен передавать все оригинальные подписанные поля без изменения.
   Настроить `PORTAL_YOOMONEY_NOTIFICATION_SECRET` и проверить обе ветки.
7. Взять БД-бэкап, проверить миграцию `10a2b3c4d5e6`, обновление XUI-клиента
   и продление на staging-панели той же версии. Разрешить backend-соединение
   к приватной панели, не публикуя её наружу.
8. Проверить тарифные лимиты против политики сброса трафика XUI. Для веб-клиентов
   объём складывается при покупке, счётчики не сбрасываются при повторе webhook.
   Политика сброса inbound должна соответствовать условиям продаж.
9. Если reverse proxy передаёт X-Real-IP, указать его точные IP/CIDR в
   `PORTAL_TRUSTED_PROXY_CIDRS`; заголовок доверяется только этим источникам.
   Без этого общий IP прокси попадёт под общий лимит отправки писем.
10. Выполнить локализационные проверки проекта и сборку; после одобрения
    production deploy — только GitHub Actions и `/opt/vpnhub/deploy.sh`.
    Проверить вход, оплату, повтор webhook, отказ панели, продление, скачивание,
    logout и действующие сценарии бота. Проверку реального платежа и письма
    согласовать отдельно, не списывать деньги автоматически.

## Что ещё не подтверждено live

Состояние на 30 сентября 2026: сайт опубликован на `https://kynnet.space/web/`,
таблицы кабинета созданы, вход через SMTP.BZ включён. Подтверждены доставка кода
во входящие Gmail, вход, сохранение сессии после перезагрузки, выход и HTTP 401
для кабинета без авторизации. `support@kynnet.space` пересылает обращения в Gmail;
проверена фактическая доставка. Страница обработки данных опубликована.

Покупка включена после публикации условий и настройки HTTP-уведомлений YooMoney.
Проверены доставка тестового уведомления провайдера и проверка подписи.
Реальный платёж и платное продление на production ещё не проверены.
Существующие клиенты 154–157 не используются для этих тестов.

Production использует `COUNT_SECOND_MOTH=2678400`: один месяц тарифа равен
31 дню. При изменении этой настройки необходимо обновить сроки на странице
условий, чтобы они соответствовали фактическому начислению.
Личный кабинет бота не объединяется с email автоматически: это отдельная задача
с подтверждением владения обоими аккаунтами.

Статический загрузчик в Google Storage, как у образца, не заменяет API,
почту, БД и оплату. При использовании зеркала кабинет должен работать как
обычная страница на проверенном HTTPS-origin; iframe с кросс-доменными cookies
не используется. Доступность домена из сетей РФ проверяется отдельно.

Основания API:
- [YooMoney: подпись уведомлений и поля платежа](https://yoomoney.ru/docs/payment-buttons/using-api/notifications)
- [3x-ui: клиенты и привязка к inbound](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/clients.mdx)

## Страница приглашения

Общая ссылка: `/web/invite`; персональная ссылка из раздела приглашений бота:
`/web/invite/{telegram_id}`. Страница предлагает сайт (для РФ без VPN) или
Telegram (для РФ с VPN), с оговоркой о зависимости доступности от сети.
Страница и переход на сайт работают без JavaScript и без вызова Telegram API.
Имя бота разрешается сервером только при выборе Telegram; назначение редиректа
строится через aiogram, произвольные URL от пользователя не принимаются.
Старые прямые Telegram-ссылки продолжают работать.

Первое действительное приглашение хранится 30 дней в подписанном Secure/HttpOnly
cookie. При запросе кода оно фиксируется в `web_challenges.referral_tgid`, при
первой регистрации — в `web_accounts.referral_tgid` (миграция `40d5e6f7a8b9`).
Повторный вход не меняет пригласившего. После входа cookie удаляется.
Счётчик приглашённых в боте включает регистрации через сайт, без раскрытия email.
Показанные в боте бонусные дни относятся к Telegram; веб-регистрация сама по себе
не начисляет реферальных бонусов. У сайта сохраняется отдельный пробный период.

Проверки: `tests/test_web_invites.py` — два пути перехода, совместимость start-кода,
первая атрибуция, подмена/истечение cookie, фиксация на момент запроса кода,
заблокированный пригласивший, повторный вход и недоступность Telegram API.

## Пробный доступ через email

`POST /web/api/trial` доступен только после подтверждения email и с тем же Origin.
Длительность берётся из `CONFIG.trial_period`, трафик — из
`get_trial_data_limit_gb()`; текущие production-параметры: 3 дня и 10 ГБ.
Предложение возвращается в `/web/api/config`, право активации — в `/web/api/account`.
Оплата и карта для пробного доступа не нужны; платёжный заказ не создаётся.

Миграция `30c4d5e6f7a8` добавляет `web_trials`. Выдача фиксируется в БД до
обращения к XUI. Блокировки аккаунта/подписки и уникальные ограничения исключают
повторное начисление. Сбой панели оставляет подписку с кнопкой повтора: используются
те же UUID, срок и лимит. Истёкший пробный период повторно не выдаётся.
Наличие незавершённого заказа не мешает пробному доступу; подтверждённая покупка
добавляет срок и трафик к той же подписке. После оплаченной подписки пробный доступ
не предоставляется, даже если она уже истекла.

Один пробный период на подтверждённый email; точки, `+suffix` и googlemail.com
у личных Gmail-адресов нормализуются только для проверки повторной выдачи.
Идентификатор хранится как HMAC с `PORTAL_SECRET`: при его ротации нужно обновить
эти значения из соответствующих email в той же операции. Защита по email не
эквивалентна ограничению на человека и не объединяет аккаунты Telegram.
Дополнительно разрешены 5 новых активаций с IP за сутки; повторная настройка
уже выданной подписки этот лимит не расходует. Доверенные прокси должны быть
заданы точно, иначе пользователи разделят лимит IP самого прокси.

Публичная страница `/web/setup` содержит инструкции Happ для Android, iPhone/iPad,
Windows/macOS и Linux, официальные ссылки загрузки и смену на резервный XHTTP.
Ссылки на инструкции доступны на главной и в кабинете до получения профилей.

Проверки: `tests/test_web_trials.py` покрывает выдачу, сбой панели, повтор,
истечение, Gmail-псевдонимы, недоступный сервер и переход к оплате. С
`PORTAL_TEST_POSTGRES=1` используются только изолированные
`localhost:15489/portal_test` и случайная схема для миграции и конкурентных запросов.

## Размещение на существующем VPS: общий 443

Подготовлена opt-in схема `configs/portal/nginx-shared.conf`. Nginx в host network
слушает только публичные IPv4/IPv6 адреса VPS на 443. SNI `kynnet.space` идёт
на локальный HTTPS 9443, остальные имена — на Xray `127.0.0.1:443`.
PROXY protocol сохраняет исходный IP. Публичные адрес, порт, UUID, REALITY-ключи
и shortId клиентов не меняются; XHTTP остаётся на 2087. Перезапуск XUI при первом
включении кратковременно переподключает VPN-клиентов.

Активация: после проверки и разрешения публикации создать root-owned файл
`/etc/vpnhub/portal-ingress.enabled`. Затем обычный GitHub Actions deploy вызывает
`/opt/vpnhub/deploy.sh`, который после готовности бота запускает
`scripts/deploy_portal_ingress.sh`. Напрямую этот скрипт на production не запускать.
Он сначала получает сертификат через HTTP-01 с существующей ACME-учётной записью,
проверяет Nginx, сохраняет SQLite backup и меняет только два поля inbound 1.
Ошибка первичного переключения автоматически восстанавливает исходный listener;
списки клиентов и сроки не откатываются. Повторный deploy делает reload Nginx.
Сертификат обновляет systemd timer `vpnhub-portal-renew.timer`.

Пока `PORTAL_ENABLED=false`, публичные тарифы доступны, но вход и платежи закрыты.
На сайте явно отображается статус подготовки запуска. Для полноценного кабинета
по-прежнему обязательны SMTP, правовые страницы и проверенные платёжные уведомления.
Перенаправление не публикует панель XUI, БД или остальные служебные HTTP-маршруты.
