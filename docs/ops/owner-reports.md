# Регулярные отчёты владельцу

Расписание: **07:00 и 21:00 Asia/Yakutsk**, ежедневно. Каналы: email и Telegram.
Реальный адрес получателя задаётся только в закрытом `bot/.env`.
Этот PR готовит первый этап; без отдельного включения отчёты не отправляются.

## Что работает в первом этапе

Отдельный Compose-сервис `ops-reporter`, без зависимости запуска от основного
бота, SSH, noVNC, PostgreSQL или Redis. Он использует существующий образ и
SMTP/Bot API, но не запускает polling и не обращается к getUpdates.

Каждый цикл проверяет `/health` (строго db=true, nats=true), Redis PING,
HTTPS сайта и сервиса подписок с проверкой сертификата, а также агрегаты
подписок и подтверждённых связей в PostgreSQL. SQL выполняется в read-only
транзакции с ограничением времени; клиентские данные и UUID не выводятся.
Подсчёт связей не является E2E-проверкой привязки или сверкой с XUI.

Три последовательных сбоя вызывают уведомление; два успешных замера —
уведомление о восстановлении. История, инциденты и очередь доставки сохраняются
в отдельном томе SQLite. У каждого канала свой статус доставки: ошибка email
не вызывает повтор успешного Telegram и наоборот. При 429 учитывается retry_after.
Все исключения журналируются только по типу, без URL, токенов и адресов.

Отчёт содержит свежий замер, статистику предыдущего интервала 21:00–07:00
или 07:00–21:00 и явные непроверенные компоненты. После перезапуска пропущенный
отчёт догоняется в течение часа; более старые отчёты не рассылаются.
Обычная точность запуска — примерно одна минута плюс время сетевых запросов.
SMTP/Bot API не дают exactly-once доставки: потерянное подтверждение после
успешного принятия сообщения может привести к повтору. Message-ID email стабилен.

## Чего этот этап не подтверждает

- HTTP-запрос с VPS не проверяет маршрут из сетей клиентов.
- Внешние тесты VLESS/REALITY 443/2087, сеть РФ, E2E привязки, XUI, внешняя
  копия и пробное восстановление требуют отдельных сборщиков.
- Остановка всего VPS остановит и этот отправитель. Для обнаружения такого
  простоя нужны внешняя точка и контроль отсутствующего heartbeat.
- Текущий heartbeat контейнера подтверждает выполнение цикла, не успешную
  доставку. Недоставленные сообщения остаются в очереди до истечения часа.
- Автоматическое восстановление подписок, смена ключей и рестарты не выполняются.

Таким образом, первый отчёт не может выдать общую зелёную оценку до подключения
недостающих сборщиков. Подключение сборщика — отдельная проверяемая работа.

## Результаты отдельных сборщиков

Доверенный администратор/сборщик атомарно записывает JSON в `ops-observations/`.
Каталог игнорируется Git и монтируется только для чтения. Это внутренний
интерфейс; его нельзя публиковать как unauthenticated API.

Имена: `vpn_primary.json`, `vpn_fallback.json`, `xui_integrity.json`,
`accounts_e2e.json`, `route_ru.json`, `backup_offsite.json`, `backup_restore.json`.
Поля: `status` (`ok` или `fail`) и `checked_at` (Unix seconds UTC).
Произвольный текст из файлов в отчёт не переносится. Для VPN/XUI/РФ срок
свежести 15 минут, для E2E/внешнего бэкапа 26 часов, восстановления — 35 дней.
Исчезновение или устаревание ранее подключённого результата вызывает сбой.
Отсутствующий с самого начала сборщик остаётся «не подключён».

## Проверка перед включением

В закрытом `bot/.env` должны быть:

```dotenv
OPS_REPORT_CHANNELS=email,telegram
OPS_REPORT_EMAIL_TO=owner@example.com
# Существующие PORTAL_SMTP_HOST/PORT/USER/PASSWORD, PORTAL_MAIL_FROM,
# TG_TOKEN, ADMIN_TG_ID, PORTAL_ORIGIN, PUBLIC_SUBSCRIPTION_BASE и Postgres.
```

Проверить, что ADMIN_TG_ID принадлежит владельцу, email согласован, SMTP готов.
Не сохранять реальные значения в PR, командной строке или журнале.
Предпросмотр не создаёт расписание/очередь и не отправляет сообщения:

```bash
docker compose --profile ops build ops-reporter
mkdir -p ops-observations
chmod 700 ops-observations
docker compose --profile ops run --rm --no-deps ops-reporter python -m ops_reporter --preview
```

После одобрения production-включения создать маркер
`/etc/vpnhub/ops-reports.enabled` через согласованный процесс эксплуатации.
Обновление/запуск выполняется только GitHub Actions → `/opt/vpnhub/deploy.sh`.
Deploy-скрипт сам не создаёт маркер и не меняет получателей. Проверить
`docker compose --profile ops ps ops-reporter`, heartbeat и реальную доставку
обоих каналов. До включения маркера расписание не активно.

Отключение: убрать маркер и остановить только `ops-reporter`; данные тома
не удалять. Эти действия относятся к production и требуют одобрения владельца.
