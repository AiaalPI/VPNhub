## Candidate permanent deployment

`configs/bridge/haproxy.cfg` uses normal 443/2087. It passes TCP to fixed IPv6
backends without terminating REALITY, logging request payloads, or holding user
credentials. It does not introduce Cloudflare. Monthly accounting still occurs
on HEL1; the bridge is not a second independent exit or a separate quota.
HEL1 sees the bridge address rather than each user's source address, which must
be considered when relying on source-IP/device limits or abuse attribution.

The manual `Deploy VPN bridge` Actions workflow runs only from main and calls
`/opt/vpnhub/deploy.sh bridge` on the new server. The normal application deploy
entrypoint retains its current behavior. Bridge configuration is validated
before activation; previous unit/config files are retained and restored if
activation fails. TCP checks are followed by an external VPN test; TCP alone
does not establish working authentication or throughput.

Before enabling this deployment:

1. Obtain the owner's explicit production approval. Do not merge or dispatch
   merely because the temporary test was authorized; merging main also starts
   the existing application deployment workflow.
2. Configure a `bridge-production` GitHub environment with a required reviewer.
3. Authorize a dedicated deployment SSH key on MOW2; store only its private half
   as the environment secret `BRIDGE_SSH_KEY`. Do not upload the Mac private key.
4. Verify the MOW2 host key through the provider console and put its exact
   known_hosts entry into environment variable `BRIDGE_HOST_KEY`.
5. Dispatch the workflow and re-run external VPN tests against 443/2087.
6. Keep the trial profiles separate until the owner confirms the phone test.
   Automated changes to exported endpoints and subscription/DNS availability
   need their own reviewed implementation and explicit cutover approval.
